## Геометрия и ограниченный ACK

На настоящем Chromium с CSS/JS Readium 3.4.0 воспроизведён конкретный геометрический отказ старого алгоритма: viewport **24 CSS px**, первый символ на **y=40.046875**, bottom=66.046875, shown=false после `scrollBy(rect.top - 40)`. Это подтверждает гипотезу как реальную ветку отказа; не доказывает, что именно она вызвала событие48 на Honor.

Новый JS-протокол:

- Выбирает первый читаемый символ диапазона. Нулевая ширина схлопнутого пробела у переноса не считается видимым символом; ищется следующий читаемый glyph, в том числе рядом с односимвольным сохранённым anchor.
- При положительной раскладке начинает прокрутку сразу, совмещая первый символ с верхом viewport. Фиксированного отступа40 нет; погрешность до1px не вызывает повторное дрожание scrollY.
- Accepted request не равен ACK. Native опрашивает один requestId в одном documentId; URL преобразуется в индекс ресурса и должен соответствовать currentLocator/цели.
- `pending`/`layout_wait` ждут положительные viewport width/height, documentReady, загруженные fonts и устойчивую геометрию. Два RAF больше не считаются универсальной гарантией: подтверждение требует повторных одинаковых измерений с интервалом не менее32ms (минимум две устойчивые проверки после исходного измерения).
- JS ограничен **4 s** на layout/видимость; native ACK guard **6 s**, context guard12s. При нулевом viewport прокрутка/успех не выдумываются: есть ограниченное ожидание, затем LAYOUT_TIMEOUT. Все native await проверяют cancellation/revision.
- Нет фонового JS-цикла или бесконечных таймеров: работа ACK выполняется при ограниченном native polling. После отмены старой операции больше нет polling/повторной прокрутки из неё. Действие pointer/touch/wheel во время восстановления завершает его RESTORE_INTERRUPTED.

Chromium проверил 24/32/40/400 CSS px, цели у начала/в середине/в конце ресурса, нулевой измеренный viewport с последующим возвратом положительной высоты и прерывание пользователем. Подтверждается фактическая видимость первого читаемого glyph. Нулевой viewport в desktop-тесте — контролируемая подмена измерения innerHeight, не Android-событие.

## Управляемое состояние после ошибки

ReaderSession различает NEW, FROZEN (например IME/смена книги), RESTORING, RECOVERING и TRACKING. `ready` соответствует только TRACKING. После отказа или обычной отмены восстановление не оставляет сессию в постоянном FROZEN. Сначала выполняется ограниченная попытка получить достоверный видимый снимок (до1.5s), затем при необходимости продолжается штатное наблюдение/capture. Мёртвого цикла повторения старой INITIAL-цели нет.

Перевод в TRACKING и запись fallback разрешены только после проверки активных book/revision, совпадения currentLocator и фактического DOM URL/documentId, канонического DOM/model, положительной устойчивой геометрии и видимости, range/quote/hash. Если это не подтверждается, новый anchor не пишется. Когда точная цель не показана, но текущая видимая точка проверена, сохраняется **эта точка** с RECOVERY в трассе и понятным статусом. Hash/quote/resource-защита не снята.

INITIAL-restore, currentLocator observer и периодический capture теперь отдельные дочерние задачи одного lifecycle-блока. Отказ INITIAL не мешает наблюдать новую главу5 или последующую корректную прокрутку. Явные кнопки перехода и новое наблюдаемое изменение ресурса прерывают прежний restore с новой revision; старый initial target не возвращается при resume. Новый resume автоматически не запускает уже отвергнутый INITIAL заново.

onPause инвалидирует незавершённый restore и пытается получить проверенный текущий снимок. Сам capture коммитит успешный результат. **Безусловный `persist()` старого JSON из onPause удалён**: комментарии/шрифт уже сохраняются при изменении, позиция — при подтверждении/capture. Если снимок недоступен/отменён, последний достоверный якорь остаётся на диске, но это явно FALLBACK/статус, а не маскирующий STORE_WRITE «текущей» позиции. Destroy по-прежнему инвалидирует старую сессию, поздние await не коммитят новое поколение.

## Дрейф при поворотах

Сохранённая подтверждённая точка удерживается в JS до реальной прокрутки/нового действия/нового programmatic go. `viewport.first/last` отражают фактически видимый текст для процента; `viewport.anchor` может сохранять подтверждённую точку, пока она видна и scrollY не изменён. Это предотвращает повторное сохранение всё более раннего начала строки после каждого поворота. При пользовательской прокрутке/смене ресурса удержание прекращается и сохраняется актуальная точка.

На Chromium восемь чередований portrait/landscape дали offsets `[1500,1500,1500,1500,1500,1500,1500,1500]`. Тест проверяет сохранение anchor при реальной перераскладке, а не пиксельную точность. Если glyph выше низкого viewport, проверяется его пересечение с областью чтения — максимальная доступная видимость без изменения кнопок.
